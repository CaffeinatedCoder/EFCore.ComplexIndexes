# Waivers of the translator parity sweep (TranslatorParitySweepTests). Every row the sweep finds
# rendering unlike EF Core is fixed or listed here under a block with its reason; a listed row the
# sweep no longer finds fails it, so this file shrinks as fixes land. See ParityWaivers for the form:
# "rule:" switches on one of PostgreSQL's own rewrites for every row, "same:" rows render differently
# and answer alike (the live sweep checks them on PostgreSQL 18), "unchecked:" rows cannot be compared
# or differ knowingly, and say why.

rule: negator
    PostgreSQL rewrites NOT over a comparison into the comparison's negator, pushes NOT through
    AND and OR, and cancels a double NOT (negate_clause, in eval_const_expressions) before it compares
    an index predicate with a query, so NOT ("Int" = 5) and "Int" <> 5 are one predicate to the
    planner and select the same rows. The translator keeps NOT (…) over operands that cannot be null
    so that filters scaffolded before 5.5.0 do not change (#68).

rule: boolean-equality
    PostgreSQL rewrites x = TRUE to x, x = FALSE to NOT x, and their <> forms to the opposite
    (simplify_boolean_equality) before planning, so "Bool" = TRUE is "Bool" to it. The translator
    keeps the comparison it was given so that existing filters do not change.

rule: integer-length
    length() returns integer, so EF Core's length(x)::int is a cast to the type the call already has,
    which PostgreSQL's parser does not put in the tree. The index on length(x) serves the query.

    A date or time member of a ToJson() document renders as text, not as EF Core's
    CAST(… AS timestamp with time zone), because that cast is not IMMUTABLE and PostgreSQL refuses it in
    an index (5.4.0). A non-unique index that starts with one is refused at migrations add.
    - expression: x => x.Doc.Date
